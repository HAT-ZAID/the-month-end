# Edge-case policy

How this solution resolves the edge cases that most often move a scored output
field. Every `file:line` citation below was verified against the working tree
when this document was written; if a citation and the code ever disagree, the
code is correct and this document should be fixed.

| Case | Policy | Rationale | Enforced at (`file:line`) |
|---|---|---|---|
| **Missing income** | A pending credit is never counted and never forecast. Income history for a recurring category uses only settled/scheduled income rows, dated by `settlement_date` (falling back to `event_date`), and forward income is forecast only for categories flagged as recurring. | Pending bonuses, commissions, refunds and other credits are not cash until they settle (AGENTS.md §6.3). Forecasting them early would inflate `amount_safe_to_pay` and pull `earliest_date_for_full_payment` forward; dating salary by anything other than its settlement date does the same. | `code/oracle.py:289` (pending credit skipped in the window loop); `code/oracle.py:152` (pending status rejected for income history); `code/oracle.py:270` (settlement date preferred over event date); `code/oracle.py:379` (income forecast loop); `code/recurrence.py:31` (`detect_recurrence` gate) |
| **Overlapping commitments** | Pending debits are reserved as upcoming cash while pending credits are ignored. Rows sharing an exact `event_id` collapse to a single survivor picked by the explicit resolution precedence. A `linked_event_id` alone never collapses a pair — only an explicit cancellation row linked to a parent removes that parent. | The same commitment can appear more than once (CSV retries, refund/debit pairs, linked transaction lifecycles). Collapsing a linked pair would drop a real cash leg; not collapsing duplicates would double-reserve cash. Resolution follows the AGENTS.md §6.3 hierarchy and the safer interpretation. | `code/oracle.py:53` (countability predicate `_is_countable`); `code/oracle.py:289` (live pending-credit skip, so pending debits remain reserved); `code/oracle.py:90` (`_dedup_events`: exact IDs only); `code/oracle.py:118` (only cancellation rows drop their linked parent) |
| **Partial feasibility for installments** | Strict mode — pinned for production runs — fails closed. An installment option is rejected if any leg falls before `request_date` or beyond the 91-point ledger horizon, if the ledger is missing, not exactly 91 points, or contains non-finite (NaN) balances, or if the request date or `minimum_balance_to_keep` floor is unparsable or NaN. A plan with one unverifiable leg is never partially credited. | A plan whose later legs cannot be simulated could silently breach `minimum_balance_to_keep` after `amount_safe_to_pay` is paid. Failing closed trades a few unavailable options for zero hidden floor breaches. | `code/solver.py:46` (`_installment_safe` fail-closed contract); `code/solver.py:70` (91-point ledger required); `code/solver.py:83` (legs beyond the horizon rejected); `code/solver.py:306` (strict gate before an option is viable); `code/main.py:137` (strict mode pinned for production) |
| **Ambiguous spending-adjustment candidates** | A stop/reduce is eligible only when the event belongs to the requesting user, is an expense/subscription debit with settled/scheduled/pending status, is flagged recurring, its category is absent from `expense_categories_to_protect`, the event has stoppable/reducible flexibility, and the action's category appears in the user's `expense_categories_user_is_willing_to_stop` / `..._to_reduce` list. At most three actions are searched, and stop and reduce are mutually exclusive for the same `event_id`. | The spec caps `spending_changes_needed` at three actions on non-protected, permitted, flexible recurring expenses. Contradictory stop+reduce plans for one event are meaningless, and ambiguity resolves toward taking no action rather than inventing a change the user never allowed. | `code/changes.py:64` (profile lists parsed); `code/changes.py:88` (recurrence evidence required); `code/changes.py:96` (protected categories excluded); `code/changes.py:98` (action must be in the user's permitted list); `code/changes.py:105` (cap of three); `code/changes.py:109` (stop/reduce mutually exclusive) |
| **Spending change acts on recurrence** | A stop/reduce suppresses the category's *future forecast* only. Settled history is never rewritten, and no saving is claimed for an already-ended subscription: events dated on/after `request_date` are upcoming cash simulated as zeroed/reduced on a **copy** of the event list, while events dated before `request_date` are history handled solely by category suppression. Savings are attributed only to a combination whose re-simulated ledger comes back safe. | History is evidence of recurrence, not spendable cash — rewriting it would misstate the past and double-count savings. The cash actually removed by a stop is the category's forward forecast; when no forward forecast remains (subscription already ended), the safety gate cannot pass, so nothing is reported. | `code/oracle.py:167` (`suppressed_categories` parameter); `code/oracle.py:335` (suppression zeroes the forecast average; history amounts stay); `code/oracle.py:278` (pre-request rows never enter the window ledger); `code/changes.py:112` (in-window rows simulated on a copy); `code/changes.py:124` (pre-request history handled by suppression); `code/changes.py:140` (a combination — and its savings — is accepted only when the simulation is safe) |
| **Unresolved evidence** | When an event's amount is blank and linked-image OCR cannot produce one agreeing figure (or OCR is unavailable), the request fails closed: `affordability_status = not_affordable`, `amount_safe_to_pay = 0`, `payment_plan = none`, no spending changes. | A blank amount must never be read as zero or guessed (AGENTS.md §6.1). Guessing could approve a payment the user cannot fund; failing closed keeps every scored field conservative and matches the unresolved-evidence warning in `decision_explanation`. | `code/evidence.py:94` (`OCR_UNAVAILABLE` / `AMOUNT_UNRESOLVED` warnings); `code/main.py:130` (any warning or invalid amount trips fail-closed); `code/main.py:41` (`_fail_closed_result` field values) |
| **Unknown FX** | If any in-window foreign-currency event has no rate dated on-or-before its settlement date for its pair (`resolve_rate` returns `None`), the whole request fails closed: `safe_amount = 0`, `earliest_date = None`, while still returning a 91-point ledger of the starting balance. The same gate covers unknown/ambiguous statuses. | Never invent a cross-multiplied rate (AGENTS.md §6.3: do not invent financial facts). A wrong rate moves both `amount_safe_to_pay` and `earliest_date_for_full_payment`; the flat 91-point ledger preserves the contract every caller and test depends on. | `code/fx.py:22` (missing rate → `None` + `FX_UNKNOWN`); `code/oracle.py:294` (flag recorded for the ledger event); `code/oracle.py:426` (fail-closed return: zero, `None`, 91 points) |

## Note: ruling T2-c (spending-change evaluation strategy)

The two mechanisms in the fifth row act on disjoint date sets. An event dated
on or after `request_date` is upcoming cash and is simulated by editing a copy
of the event list; an event dated before `request_date` is history, never
reaches the 91-point window ledger, and is therefore handled by category
suppression alone. The search validates every candidate combination with both
mechanisms, and the solver re-evaluates an accepted change set with the same
semantics before any changed option becomes viable:

- `code/changes.py:112` — copy edit for in-window upcoming cash
- `code/changes.py:124` — suppression for pre-request history
- `code/solver.py:417` — solver re-evaluation under the search's semantics
