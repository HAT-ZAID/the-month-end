## Verdict: **BLOCK**

The eligibility widening (item 1), recomputation rule (item 3), partial-leg arithmetic (item 4), copy-edit path (item 5), and output-format validity (item 6) all pass on real data. The block is driven by **F1**: three of the four emitted change rows claim `affordable_with_plan` only because `reduce_to` zeroes the category's whole forward forecast, while the emitted action — executed literally — frees strictly less cash than the request needs. **F2** additionally falsifies a guarantee the repo writes about itself (`docs/edge-case-policy.md:14`). **F3** is a latent spec violation in the same code path.

## Explicit answers to gate items 1–6

### 1. Candidate widening (`changes.py`) — eligibility filters
**PASS.** Monkeypatched `code.changes.combinations` to capture the filtered candidate set across a full in-memory rerun:
`search_changes` reached for **76/250 requests, 1195 total candidates — VIOLATIONS: protected=0 income/credit=0 non-recurring=0 wrong-user=0 bad-status=0 bad-flex=0 not-permitted=0**.
Synthetic defenses also hold: adding `streaming|shopping` to `expense_categories_to_protect` while `shopping` remains reduce-permitted → `changes=[]` (shopping excluded solely by the protect guard); a crafted `event_type=income, direction=credit` row in a stop-permitted category → excluded (no `inc_test` target); a one-time stoppable expense in a non-recurring category that is in the stop list (`once_test`, electronics) → excluded (`changes=['stop:event_7192','reduce_to:event_7201:1480']`, no `once_test`). Note (design fact, not a violation): a one-time row **inside** a flagged recurring category would be targetable — the guard is category-level, matching edge-case-policy's wording.
Also verified: no date-window filter by design (`changes.py:56-58` comment); flags matched with the same lowercasing on both sides as `recurrence.detect_recurrence` keys raw tuples.

### 2. Suppression savings are not phantom money
**PASS on real data; written guarantee falsified synthetically (F2).** The only subscription stop emitted anywhere (`stop:event_7192`, request_78) targets an **ongoing** subscription (last charge 2025-09-10, cadence 31d → next due ~2025-10-11, inside the window): suppression removes real future cash. No `user_78` messages exist (no cancellation evidence), and the dataset contains no genuinely terminated subscription (451/451 subscription categories have gap < cadence). However, the edge-case policy's stated *mechanism* ("when no forward forecast remains … the safety gate cannot pass") can never trigger — probe A above shows a stop is emitted for a subscription ended 180d before the request. One-time/non-recurring targets: never emitted (0 in 1195 candidates; synthetic probe confirms).

### 3. `solver.py` recomputation & pre-change earliest rule
**PASS.** All 4 change rows re-evaluate through `solve_safe_amount(..., suppressed_categories=suppressed_cats)` (`solver.py:438-439`). Output `earliest_date_for_full_payment` is the **base** (`res_now`) earliest on every change row (`solver.py:475`), honoring the "earliest date" rule before optional changes:
- request_78: base-safe 45888.78 (OCR), base earliest **2025-11-16** = output; res2 with `suppressed_categories=['shopping','streaming']` gives safe 50200 / earliest 2025-10-02 — output keeps 2025-11-16. ✓
- request_99 / 117 / 135: same pattern (base earliest 2026-07-15 kept where res2 earliest would be earlier).
`affordable_now` consistency: all 66 `affordable_now` rows have earliest == request_date.

### 4. Partial-payment leg arithmetic
**PASS.** All 8 partial rows (`request_56,138,168,210,214,248,260,273`) pass: exactly 2 legs; leg1 == `amount_safe_to_pay`; leg1 + leg2 == `requested_amount` exactly; leg2 date == `earliest_date_for_full_payment` column; `0 < safe < requested`. Dataset-wide, `requested_amount` never exceeds 2 decimal places, so `_money_plan`'s leg re-derivation cannot introduce rounding drift. (Latent exception only via F3, which does not occur in real output.)

### 5. Copy-edit path ("dead path") harmlessness
**PASS (harmless; comment inaccurate — F4).** The rewrite still exists at `changes.py:114-123` and `solver.py:421-437` (it is **not** removed from the code), but for every real row it cannot change the result beyond suppression: copy+sup == suppression-only exactly for all four combos; `search_changes` does not mutate the caller's event list (`False`); for pre-request targets the edit is dominated by suppression (each edited row's category is always in the same combo's suppression set). The intended in-window behavior (edit real upcoming cash on a copy) remains correct and conservative for other rows of the category (they are not zeroed → under-claim, not over-claim).

### 6. Emitted change rows: format & validity
**PASS.** Exactly 4 of 250 rows carry changes (`request_78` with 2 actions, `request_99/117/135` with 1 each): all ≤ 3 actions; formats `stop:<event_id>` / `reduce_to:<event_id>:<amount>` parse; all 5 target IDs exist, belong to the requesting user, are expense/subscription debits with settled status, flexibility-reducible/stoppable, non-protected, category in the user's permitted list, and recurrence-flagged.

## What could not be verified

1. **Hidden gold semantics for `reduce_to`'s forward forecast (the crux of F1).** The problem statement never defines what a reduction does to future occurrences; the repo documents zeroing (`docs/edge-case-policy.md:14`), and the gold samples are non-adjudicating: under the samples' own reported bases both readings clear the request (sample_11 honest gain 684,072.55 ≥ shortfall 599,355; sample_21 clears via its stop leg), and under this code's reproduction their bases already reach the request cap. Whether the evaluator's reference oracle charges 0 or `<new_amount>` after a reduce is unknowable from this repo.
2. **`tools/verify_samples.py` status: 75 mismatches across the 25 gold samples** (e.g., samples `request_06/11/21` come back `affordable_now` + `spending_changes_needed=none` while gold shows `affordable_with_plan` + changes; `request_01` emits a reduce gold does not). Root causes sit in the **base ledger / evidence layer** (mixed directions vs gold, and that tool runs without OCR), i.e., outside these two features; sample-exact matching is explicitly deferred (`plan_a.md:37`, `docs/superpowers/plans/...compliance-fixes.md` Task 5). Not counted as a gate finding, but it means samples cannot be used to validate this feature either.
3. **Terminated-subscription frequency in the evaluator's own data** — the provided dataset has none (gap ≥ 2× cadence), so F2's real-data exposure is zero here but unknown for hidden data.
4. **F3's reachability in a full run** — only demonstrated synthetically through `solve_request`; real 250-request output contains no `opt_partial_changed` row (all 4 change rows are full-changed; all 8 partial rows are no-change).
